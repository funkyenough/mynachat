Architecture

System overview

Everything personal stays on the member's side. The group runs two small services. One relays encrypted bytes. The other takes part in the TLS session as an MPC peer, so it can confirm where the data came from without ever seeing it.

Protocol

One verification, step by step

The member logs in normally. The extension then opens one fresh TLS connection to Myna Portal, run jointly with the verifier, and replays the single request that returns the certification.

Trust model

Remove the third party

A notarized proof is only as honest as its notary. When the group itself is the MPC peer, the one party that must not collude with the prover is the party making the decision.

Phase 3

Tie the proof to the card holder

A Myna Portal session proves an account has the certification. It does not prove the person in front of us owns that account. The card's JPKI signing certificate closes the gap, and a zero-knowledge proof keeps the matching fields hidden.

How we proceed

Roadmap with decision gates

Phase 0 decides whether the main path works at all. Each gate has a fallback that rejoins the main line, so a "no" changes the route but does not end the project.

Phase 0 capture checklist

  • Log in to Myna Portal on desktop with DevTools open, Network tab, Preserve log on.
  • Open the page where a certification would show. Filter to Fetch/XHR and find the call that returns it.
  • Note host, path, method, the names of auth headers or cookies, content type, and response size.
  • Run the same openssl s_client -tls1_2 probe against that host.
  • On your own machine, replay the call with curl using only the token, to confirm it works outside the page.
  • Bring back a redacted description: structure and field names, with dummy values.

Keep secrets local. Don't paste tokens, cookies, or real medical fields into chat or the repo. Field names and shapes are all we need.
